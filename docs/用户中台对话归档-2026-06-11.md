## 2. 应用隔离结论

当前已经实现的是第一层应用隔离：

- 用户登录某个应用时，会校验用户是否拥有该应用下的角色。
- 用户可以通过直接授予角色，或者通过组织继承角色获得应用访问权。
- 没有对应应用角色时，`/oauth/authorize` 会返回 `access_denied`。

还未实现的是第二层 API 鉴权：

- 前端菜单和按钮控制只是体验，不是真正安全边界。
- 后端 API 必须鉴权。
- 推荐后续加网关，由网关统一校验 JWT、`aud`、路径和权限点。

## 3. SSO 登录流程

目标体验类似 Keycloak：

1. 用户直接访问业务应用页面，例如报表应用。
2. 前端发现没有本应用 Token，跳转到用户中台 `/oauth/authorize`。
3. 用户中台发现没有 `UC_SSO_SESSION`，跳转统一登录页 `/sso-login.html`。
4. 用户登录成功后，用户中台写入 `UC_SSO_SESSION`。
5. 用户中台校验用户是否有目标应用角色。
6. 有权限则生成 authorization code，跳回业务应用。
7. 业务应用用 code 调 `/oauth/token` 换 Access Token。
8. Access Token 是真实 JWT。

重要结论：

- SSO Cookie 证明“用户在用户中台登录过”。
- Authorization Code 证明“本次对某个应用授权成功”。
- Access Token 是给具体应用/API 使用的令牌。
- 用户可以同时拥有多个应用 Token，例如 MES Token 和 Report Token。

## 4. Token 字段含义

Access Token 已改成真实 JWT，包含：

- `iss`：签发者，例如 `user-center`
- `sub`：用户 ID
- `aud`：Token 的目标应用/API，例如 `report-web`、`mes-api`
- `azp`：发起授权的客户端
- `sid`：应用登录会话 ID
- `iat`：签发时间
- `exp`：过期时间
- `jti`：Token 唯一 ID

`Token.aud == mes-api` 的意思是：这个 Token 是发给 `mes-api` 用的。网关或后端应该拒绝拿 `report-web` Token 调 `mes-api`。

## 5. 组织继承角色

当前只保留“组织继承”，不再做岗位/分组。

规则：

- 角色可以绑定到组织。
- 用户加入组织后，自动继承该组织绑定的角色。
- 子组织用户会继承父组织绑定的角色。
- 用户移出组织后，该组织带来的继承角色自动失效。
- 有效权限 = 用户直接角色 + 用户所在组织及父组织角色。

已存在/已新增的组织接口：

- `POST /api/v1/org-units/{id}/roles`
  - 给组织绑定角色。
- `DELETE /api/v1/org-units/{id}/roles/{roleId}`
  - 从组织移除角色。
- `POST /api/v1/org-units/{id}/users/{userId}`
  - 单个用户加入组织。
- `DELETE /api/v1/org-units/{id}/users/{userId}`
  - 单个用户移出组织。
- `POST /api/v1/org-units/{id}/users`
  - 批量添加组织成员。
  - 请求体：
    ```json
    {
      "userIds": ["user-1", "user-2"]
    }
    ```
- `GET /api/v1/org-units/{id}/roles`
  - 查询直接绑定在该组织上的角色。

## 6. 登录某个应用是否必须有 user-center-console 角色

不需要。

现在逻辑是：用户访问哪个应用，就用哪个应用的 `clientId` 登录和授权。

例如：

- 访问报表应用时，统一登录页使用 `clientId=report-web`。
- 用户只要有 `report-web` 下的角色，就可以登录报表。
- 只有登录用户中台控制台本身时，才需要 `user-center-console` 的角色。

之前的问题是统一登录页硬编码了 `clientId=user-center-console`，导致 `pym` 虽然有报表角色，但会因为没有用户中台控制台角色而登录失败。该问题已修复。

## 7. pym 登录报表问题

曾经出现的问题：

- `pym` 在组织中。
- 组织绑定了 `report-web` 的角色。
- 有效权限查询能看到报表角色。
- 但访问报表应用登录失败。

原因：

1. 统一登录页之前固定用 `user-center-console` 登录。
2. `pym` 没有 `user-center-console` 角色，所以登录阶段失败。
3. 后来修复为从 OAuth `return_to` 中解析目标应用 `client_id`。

另一个坑：

- `application.yml` 原来配置了 `spring.jpa.hibernate.ddl-auto: create`。
- 每次重启会重建表，导致运行中创建的用户、组织和角色绑定丢失。
- 已改为默认 `update`：
  ```yaml
  spring:
    jpa:
      hibernate:
        ddl-auto: ${JPA_DDL_AUTO:update}
  ```

## 8. 退出登录语义

### `/api/v1/auth/logout`

退出当前应用会话。

- 请求体：
  ```json
  {
    "refreshToken": "当前应用的 refreshToken"
  }
  ```
- 只注销这个 refreshToken 对应的应用会话。
- 不清理 `UC_SSO_SESSION`。
- 所以再次访问应用时，如果 SSO Cookie 还在，可以静默重新授权。

### `/api/v1/auth/logout-all`

全局退出。

- 清理当前用户所有应用会话。
- 注销当前用户的 SSO 会话。
- 清除浏览器里的 `UC_SSO_SESSION`。
- 调用后，同一浏览器里的所有应用再访问都要重新统一登录。

这和 Keycloak 类似：同一浏览器、同一用户中心域名下，普通窗口共享一份 SSO Cookie。

## 9. 为什么两个浏览器窗口会一起重新认证

如果只是打开同一个 Chrome/Edge 的两个普通窗口，它们共享同一份 Cookie。

`UC_SSO_SESSION` 挂在 `localhost:8081` 下，因此：

1. 窗口 A 登录 `pym`，写入 `UC_SSO_SESSION=pym的会话`。
2. 窗口 B 登录 `admin`，会覆盖同一个 Cookie 为 `UC_SSO_SESSION=admin的会话`。
3. 调用 `/logout-all` 后，浏览器删除这个共享 Cookie。
4. 两个普通窗口都没有 SSO Cookie，所以都要重新统一登录。

如果要同时测试两个账号，需要用隔离环境：

- 一个普通窗口 + 一个无痕窗口。
- Chrome + Edge。
- Chrome 不同用户 Profile。
- 不同浏览器上下文。

注意：这不代表服务端一定把两个用户都注销了，而是浏览器共享的 SSO Cookie 被清掉了。

## 10. logout-all 的已修复问题

之前 `CurrentUserProvider.userId()` 没拿到用户时默认返回 `user-001`，也就是 admin。

这会导致：

- 用 `pym` 浏览器调用 `/logout-all`。
- 浏览器侧清掉 pym 的 SSO Cookie。
- 服务端侧却可能按 admin 注销会话。

已修复为：

1. 优先读取 `X-User-Id`。
2. 其次根据当前请求的 `UC_SSO_SESSION` 找到 SSO 会话所属用户。
3. 最后才使用开发默认 `user-001`。

## 11. 资源和权限点关系

资源是“页面、菜单、按钮、API、报表”等被保护对象。

权限点是“允许对某个资源执行某个动作”的授权单位。

例如：

- 资源：`/report/monthly`
- 权限点：`report_monthly_view`
- action：`view`

创建权限点时绑定 `resourceId`，是为了让权限点能关联到具体菜单、按钮、API 或报表资源。后续前端渲染菜单按钮、网关匹配 API 权限，都可以通过资源和权限点的关系完成。

## 12. 前端应用和后端应用接入关系

真实业务系统通常有：

- 前端应用，例如 `mes-web`
- 后端 API，例如 `mes-api`

前端负责：

- 跳转用户中台登录。
- 获取本应用 Token。
- 展示菜单、按钮、页面。

后端负责：

- 校验 Token。
- 校验 `aud` 是否是自己的 API。
- 做 API 权限判断。

前端隐藏按钮只是体验优化，不能作为安全边界。

## 13. 网关方案建议

后续可以加一个轻量网关做第二层应用/API 鉴权。

网关处理流程：

1. 接收请求。
2. 读取 `Authorization: Bearer xxx`。
3. 使用用户中台 JWKS 验 JWT 签名。
4. 校验 `iss`、`exp`、`aud`。
5. 根据 `method + path` 匹配权限点。
6. 查询或缓存用户有效权限。
7. 有权限则转发到业务后端。
8. 无权限返回 403。

示例配置：

```yaml
routes:
  - path: /mes-api/**
    audience: mes-api
    target: http://localhost:9001

permission-rules:
  - app-id: mes-api
    method: GET
    path: /mes-api/orders/**
    permission: mes_order_view
```
